# 每日复盘数据安全修复设计

## 背景与目标

当前应用把所有浏览器数据保存在同一个 `daily-review` 键中，并使用一个不区分用户的同步标记。异步加载和防抖保存也没有绑定渲染日期。结果可能是账号之间串数据、旧请求覆盖新页面、断网时错误上传、云端或本地记录被静默覆盖，以及界面显示“已保存”但实际失败。

本设计采用非破坏式复制与合并。目标是把现有浏览器数据安全归属到已确认的 GitHub 账号 `Redcatancy`，同时保证迁移、同步、冲突处理和后续保存都不会静默删除原始数据。

## 范围

本轮修复以下重点问题：

- 旧 `daily-review` 数据的永久快照和一次性迁移。
- 登录用户、其他用户和访客之间的本地数据隔离。
- 可区分成功、空结果和失败的云端同步。
- 本地与云端记录的非破坏式合并和冲突归档。
- 本地优先保存、待同步队列、失败重试和真实状态提示。
- 快速切换日期或页面时的异步竞态。
- 日记防抖保存、页面离开前刷新以及清空日记。
- 可下载的数据备份。
- Supabase 唯一约束和行级安全策略。
- 针对上述规则的自动测试。

日历查询性能、日历月份按钮行为、历史日期分析和移动端滚动不在本轮范围内；它们不会影响本次数据格式和迁移安全。

## 核心不变量

实现必须始终满足以下约束：

1. 迁移前的旧 JSON 必须先按原文备份，备份写入验证成功后才允许复制数据。
2. 自动流程不得删除旧 `daily-review`、迁移快照或冲突归档。
3. 任一用户只能读取自己的本地命名空间和通过 Supabase RLS 授权的云端行。
4. 云端读取失败不得被解释为“云端为空”，失败后不得触发覆盖性上传。
5. 合并不得丢弃任何非空字段；无法确定新旧的数据必须进入冲突归档。
6. 界面只有在本地写入成功后才能显示“已保存到本地”；只有云端确认成功后才能显示“已同步”。
7. 异步响应只有在用户、日期和渲染版本仍匹配时才能更新界面。

## 本地存储模型

保留现有 `daily-review` 作为只读旧源，不自动删除。新增键遵循以下格式：

- `daily-review:legacy-backup:v1`：首次迁移前保存的旧 JSON 原文、创建时间和校验信息。
- `daily-review:legacy-claim:v1`：记录旧源首次归属的用户 ID，阻止同一旧数据再次复制给其他账号。
- `daily-review:user:<supabase-user-id>:entries`：指定登录用户的日记录。
- `daily-review:guest:entries`：未登录访客的新记录。
- `daily-review:user:<supabase-user-id>:outbox`：尚未成功同步的日期及字段。
- `daily-review:user:<supabase-user-id>:conflicts`：同一日期同一字段出现不同非空值时保存的双方版本。
- `daily-review:user:<supabase-user-id>:migration`：迁移完成标记和旧源摘要。

所有写入采用“生成完整新值、写入、立即读回并验证”的顺序。写入失败时保留原键，返回结构化错误，不继续同步。

## 旧数据迁移

用户已确认当前浏览器里的旧数据全部属于 `Redcatancy`。应用获得该账号的 Supabase 用户 ID 后执行一次迁移：

1. 读取 `daily-review` 的原始字符串；不存在时记录“无旧数据”并结束。
2. 解析并验证数据是以 `YYYY-MM-DD` 为键的对象；解析失败时保存原始字符串到备份并停止自动合并。
3. 如果 `daily-review:legacy-backup:v1` 不存在，先写入完整原文和时间，再读回确认内容一致。
4. 写入并验证一次性归属标记；后续其他账号不得再次认领旧源。
5. 把合法旧记录复制到当前用户命名空间。目标日期不存在时直接复制；存在时执行字段级非破坏式合并。
6. 将所有需要上传的本地字段加入 outbox。
7. 写入迁移完成标记。旧源和备份继续保留。

迁移必须幂等：刷新、重复登录或中途失败后重试，不得生成重复记录或覆盖已经归档的冲突。

## 合并与冲突规则

记录按日期合并，字段粒度为 `checkin`、`highlights` 和 `diary`：

- 只有本地值：保留本地值并加入 outbox。
- 只有云端值：复制到当前用户本地空间。
- 双方值深度相等：保留一份，不产生冲突。
- 双方都有不同的非空值：云端值作为当前可见基线，本地值和云端值连同日期、字段、发现时间写入冲突归档；不得自动覆盖任一原始版本。
- 明确删除使用删除标记，不把空字符串、空数组或 `null` 与网络错误混为一谈。

备份导出包含当前用户记录、outbox、冲突归档、迁移信息和旧数据快照，下载为带时间戳的 JSON 文件。

## 云端同步状态机

云端访问返回可判别结果：`success(data)`、`empty` 或 `failure(error)`。同步流程为：

1. 先完成本地迁移和本地写入验证。
2. 分页读取当前用户全部云端记录，避免受单次行数上限截断。
3. `failure`：保持本地数据和 outbox 不变，显示待同步状态，不执行上传。
4. `empty`：把 outbox 和本地有效记录上传，但不删除本地内容。
5. `success(data)`：执行字段级合并，再逐条发送 outbox。
6. 只有某条云端写入确认成功后，才从 outbox 删除对应字段。

同步状态按用户 ID 保存，不再使用全局 `synced` 布尔值。登录、退出和账号切换都会切换命名空间并重新渲染当前页面，但不会清除任何用户数据。

## 编辑与异步安全

- 打卡、亮点和日记的加载都携带用户 ID、日期和递增渲染令牌。返回时任一条件不匹配就丢弃该响应，且不得修改共享状态。
- 日记防抖器绑定单次渲染，输入事件立即捕获标题、正文和日期，不在延迟回调中读取可能已经变化的全局 DOM。
- 切换标签、切换日期、退出登录和 `pagehide` 时刷新待执行的日记保存。
- 清空标题和正文会保存明确的日记删除标记，并同步到云端；不得因为两者为空而直接返回。
- 同一日期的云端写入按顺序执行；较旧版本不得在较新版本之后覆盖云端。

## 用户反馈与恢复

保存状态分为：

- `已保存到本地`：本地写入已验证，云端尚未确认。
- `已同步`：对应变更已获云端确认。
- `已保存到本地，等待网络同步`：云端不可用，outbox 保留。
- `本地保存失败，请立即导出备份`：浏览器存储配额、权限或序列化失败。
- `发现数据冲突，双方版本已保留`：冲突归档已经写入并验证。

认证区域增加“导出数据备份”入口。导出只读取当前用户及旧迁移快照，不包含其他用户命名空间。

## Supabase 安全边界

仓库新增幂等 SQL 迁移，确保：

- `daily_entries` 具有 `(user_id, date)` 唯一约束。
- 启用 Row Level Security。
- `select`、`insert`、`update` 和 `delete` 都要求 `auth.uid() = user_id`。
- `updated_at` 使用服务器侧时间或由服务器验证，客户端时间不作为覆盖顺序的唯一依据。

前端的用户过滤只用于查询效率，不作为授权边界。SQL 文件只提交到仓库；应用到远端数据库需要单独确认和执行。

## 代码边界

- `src/store.js`：保持现有公开 API，编排本地保存和同步结果。
- `src/local-store.js`：命名空间、旧数据迁移、快照、outbox、冲突归档和导出。
- `src/cloud-store.js`：Supabase 分页读取、顺序写入和结构化结果。
- `src/checkin.js`、`src/highlights.js`、`src/diary.js`：渲染令牌和输入快照。
- `src/main.js`：账号/日期/标签切换前刷新保存，切换后重新渲染。
- `supabase/migrations/20260713_daily_entries_rls.sql`：唯一约束与 RLS。
- `tests/`：使用 Node 内置测试运行器和可注入的 localStorage/Supabase 替身，避免新增测试依赖。

## 测试与验收

自动测试至少覆盖：

- 旧数据先备份后迁移，旧键保持不变。
- 迁移中断后重试仍然幂等。
- `Redcatancy` 与第二个账号、访客的数据互不可见。
- 云端读取失败时不上传、不清空、本地 outbox 保留。
- 本地独有、云端独有和同字段冲突三类合并结果。
- 冲突双方都能从导出文件中恢复。
- 快速切换日期时旧响应不能更新新页面。
- 日记防抖保存绑定正确日期，页面离开前刷新。
- 清空日记能够本地保存并进入同步队列。
- localStorage 写入失败时不显示成功。
- 云端写入确认前不清理 outbox。
